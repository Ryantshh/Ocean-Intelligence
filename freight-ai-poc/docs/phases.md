Before implementation: inspected workspace status, existing cloud ingestion, database query
models, README and glossary. Existing uncommitted changes are outside this package.

## 1. Discovery
Read both actual TEST files with openpyxl: three rows each, one sheet each,
12 Order and 16 Tonnage headers. Exact mappings and file hashes are generated by
`freight-ai inspect`. No source order ID, assignment, latitude, longitude, route
distance or usable cargo capacity exists. `ETA Dates Start` is not `ETA` and is
not readiness at the cargo load port. The legacy cloud schema is not reused:
it assumes different source fields, embeddings, and synthetic order links.

## 2. Canonical preprocessing
Explicit header mapping; nullable typed records; positive DWT and nonnegative cargo
weights; ordered ranges; content-based snapshot IDs; file/hash/sheet/row provenance.
Unknown headers fail loudly, invalid rows enter a rejection report, formula cells
require review. Missing values stay missing. Snapshots are retained, never silently
deduplicated. Content IDs change if records change; no stable business order ID
can be inferred from these files.

Phases 1–2 validation: actual-file ingestion test and preprocessing smoke passed;
all six records accepted, no source files modified. Inspection saved under data/processed.

## 3. Baseline inference
Inspected the package's schema and legacy hosted inference boundaries. Added a lazy
Transformers backend with configurable model/revision/device, greedy generation,
seed, context overflow rejection and explicit CPU/MPS vs CUDA behavior. A scripted
backend exists strictly for tests. No hosted API or database is used.

## 4. Prompt strategies
Inspected baseline interfaces; added shared schema prompt and zero/one/three-example
message construction. Demonstrations must be labelled train. JSON is parsed strictly,
unsupported fields fail closed, and explanations consume authoritative tool results.
Phases 3–4 validation: six tests passed including strategy lengths, forbidden fields,
strict parsing and demonstration rejection. Real model smoke is tracked in integration.

## 5. Behavioral dataset
Inspected schema and prompts before generation. Added reproducible, independently
authored synthetic phrasing families: 66 train, 18 validation, 18 test examples.
Source workbook rows are never inputs to generation. These examples teach intent
JSON, summary routing, match routing, conceptual QA routing and clarification.
Split families and normalized questions are checked for overlap; manifests checksum
every split. Conceptual targets may recur across splits (intentionally shared skills).
Validation: seven tests passed; generation and checksum verification smoke passed.
Limitation: narrow synthetic corpus, no claim of robust freight expertise. Broader
expert-reviewed QA/explanation and constraint examples are needed for meaningful SFT.

## 6. QLoRA SFT
Inspected split checks and baseline loader. Added TRL SFTTrainer with conversational
prompt/completion data, completion-only loss, NF4 double quantization, PEFT LoRA,
validation each epoch, saved checkpoints/adapter/tokenizer and provenance manifest.
Test rows are audited for leakage but never passed to Trainer or used for selection.
Training refuses unsupported hardware and existing adapter outputs.

## 7. Adapter inference
Inspected the base loader and saved manifest contract. Same inference backend loads
a PEFT adapter only when base model and revision match its manifest. Same prompts,
decoding and schema validation apply. CUDA training execution remains hardware-dependent;
the current host is Apple Silicon. No trained adapter or quality gain is claimed.

Phases 6–7 validation: installed Torch/Transformers/PEFT/TRL in the isolated environment;
imported SFTTrainer and SFTConfig successfully. Training preflight returns an explicit
CUDA requirement before any training starts. Adapter runtime awaits a trained artifact.

## 8. Freight engine

inclusive interval filters, complete-set aggregations with missing counts,

exclusions from unresolved checks and exposes every score component, configured
weight, assumed capacity and optional sourced-coordinate distance. Never creates
vessel–order assignments. Validation: 11 tests and actual-source screening passed.
